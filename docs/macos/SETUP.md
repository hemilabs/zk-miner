## Resident Metal hardware guidance

The current po2-20 resident Metal configuration is intended for a **64 GiB-class
Apple Silicon Mac or larger**. Validation has used an Apple M5 Max with 128 GiB;
64 GiB capacity itself has not been tested. On the WP7 branch, the default host
reserve is **8 GiB**; the configured range remains 8..64 GiB. Admission requires
normal kernel memory pressure and accounts for the measured resident worker and
helper footprint. As a secondary check, the conservative VM estimate must cover
the reserve plus at most 8 GiB of projected additional owned footprint. For a
fresh worker with a 24 GiB budget, that floor is 16 GiB of estimated headroom.
The ledger still bounds total commitments. After admission, the worker guard
continues at normal or warning kernel pressure while owned footprint is
readable and within 32 GiB. Critical pressure, an unreadable pressure or
footprint signal, or excess owned footprint stops the worker. The conservative
VM estimate is logged with a per-second minimum, not used as an in-proof kill
rule. Installed RAM alone does not establish admission.

The original campaign's largest worker/helper footprint was 16.305 GiB; the
review's warmed proof groups reached 19.783 GiB. These observations exclude
other retained workers and host processes; they are not worst-case bounds.
The post-refresh serial regression used an explicitly recorded 12 GiB reserve;
the earlier controlled final reading used the then-default 16 GiB reserve.
A smaller-machine po2-18 profile has not been validated. Lowering the segment
cap alone is not documented as establishing support for a 32 GiB Mac.

The [WP7 validation](evidence/phase2-wp7-validation.json) used the new default
reserve with Brave, Zed and Colima running. A 10M arithmetic proof verified
with an admission-wait upper bound of 0.212 s. With 64 GiB of sibling memory
held, another 10M proof admitted at 20.17 GiB estimated, reached 8.04 GiB
minimum during proving, and verified. A real warning-pressure allocation
caused a typed refusal naming level 2 and preserving the raw estimate before
worker dispatch; the next proof verified after pressure returned to normal. The earlier
[12 GiB override spot check](evidence/rv32im-desktop-admission-spot-check.json)
belongs to the pre-WP7 policy.

uses a Darwin ARM64 Go child and the shared in-process witness evaluator.
Keep the CPU/Metal reference binaries in their existing directories.

For normal supervisor launches, select the native worker binary and set
`ZKMINER_RISC0_WRAP=native`, `ZKMINER_RISC0_NATIVE_DIR` to the absolute runtime
bundle directory, and `ZKMINER_RISC0_WORK_ROOT` to an existing writable directory.
The supervisor creates a request lease and passes `RISC0_GROTH16_NATIVE_DIR` and
`RISC0_WORK_DIR` internally. No Docker context is required in this mode.
Native builds default to 18 Rayon threads and Go concurrency 18. Set
`ZKMINER_RISC0_CPU_THREADS` in `1..=18` to override Rayon; otherwise the worker
uses `RAYON_NUM_THREADS`, then its native default. `env.sh` follows the same
precedence. `RISC0_GROTH16_NATIVE_THREADS` sets Go concurrency in `1..=18`.
Malformed or out-of-range thread settings fail startup. Legacy wrapping builds
retain their six-thread fallback when launched without these environment values.
`RISC0_GROTH16_NATIVE_TIMEOUT` sets a stage budget in `1..=1800` seconds
(default 1800); the supervisor's watchdog covers synchronous witness generation.
`ZKMINER_RISC0_MAX_GUEST_CYCLES` configures the session ceiling in `1..=67108864`.
Native builds default to 67,108,864 guest cycles (64 Mi); legacy Mac wrapping
builds retain their 4,194,304 default. The executor enforces the limit during
execution, and completed guest counts are checked again. Invalid configuration
fails startup. Native segment caps are po2 14..20, with selected default 20;
legacy Mac wrapping builds retain 14..18 and default 18. The po2-18 large-job
screen completed before increasing the segment bound. Po2 20 passed five measured
warm proofs per 10M fixture and the twenty-request lifecycle gate.

The shared executor pads a final segment to at least po2 14 when its configured
cap is 14 or greater. Execution-only circuit tests can still select cap 13;
the Mac proving worker rejects that setting. Padding preserves guest cycles,
paging, the journal and the receipt claim, while increasing total/reserved
cycles where needed. Native `ExecuteResult.cycles` now sums padded segment
sizes, matching `ProofResult.cycles`; the SDK's `SessionInfo::cycles()` itself
counts guest cycles and is checked separately against the session ceiling.

Native preflight validates artifact hashes before the existing ten-second
handshake deadline; graph preparation is lazy on the proof path. Native children
inherit the owned worker group, exit if their parent disappears, and have an
internal Go deadline. Output streams are discarded and proof JSON is bounded.
The watchdog samples worker and owned helper physical footprints using
`proc_pid_rusage` once per second, under a combined 32-GiB ceiling and an 8-GiB
estimated host-headroom floor. It records worker/helper RSS separately. These
are sampled observations, not a kernel-enforced allocation cap or an exact peak;
shared charges can make the group sum conservative. Native mode uses no container
lease. The original Docker path remains the default for earlier worker builds.

Native CPU RISC0 admission starts with a 16-GiB unmeasured proof budget;
Poseidon2 recursion Metal starts at 20 GiB after its measured 17.3-GiB startup
group peak. Sampled group peaks then feed the existing calibration margin. Resident footprint of
the owned worker group supplies the existing resident-memory credit. The host
estimate remains free pages plus half the smaller of file-backed and inactive
pages, with no separate credit for compression. It is not an allocation guarantee.
`ZKMINER_MACOS_HOST_RESERVE_GIB` accepts 8..64 (default 16); invalid values refuse
admission. Host estimates and process footprints are reported separately.

New admission requires normal kernel memory pressure. Warning pressure blocks
new proofs while allowing an in-flight proof within its other bounds; critical
or unknown pressure stops the owned group. The sysctl returns dispatch pressure
flags, rather than the kernel's internal enum; see Apple's
[XNU conversion and sysctl implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus_notify.c).
API background: Apple's [memory-footprint guidance](https://developer.apple.com/videos/play/wwdc2022/10106/).
See BENCHMARKS.md for measured outcomes and limitations.

## Controlled CPU/Metal benchmark

Use the existing Command Line Tools to compile the read-only telemetry helper


The dedicated helper VM must already be running with six CPUs and 32 GiB, with
no leftover containers. The unrelated default VM remains unchanged at four CPUs
and 8 GiB. Keep the existing six Rayon threads, 24 GiB helper cap, 32 GiB worker
RSS ceiling, memory-pressure guard and 600-second proof watchdog. Each trial has
a separate 900-second acceptance bound. No limit is relaxed for benchmarking.

A fresh RISC Zero request needs at least **22 GiB of the production host-available
estimate**: its six-GiB reservation plus the 16 GiB host reserve. Leave several
additional GiB of headroom for changing application and VM usage. This estimate
is free pages plus half the smaller of file-backed and inactive pages; it is not
the machine's installed memory or a guarantee of allocatable RAM. Existing
applications and the default VM are left running. If admission refuses a trial,
the campaign stops and preserves the failure; reduce unrelated memory use only
with the user's authorization before starting a new campaign.

The runner uses the same sealed Metal-capable worker binary for explicit CPU
and forced-Metal modes. It retains one complete verified warmup per mode, then
runs five alternating CPU/Metal pairs. Every trial creates a fresh WorkerPool;
OS/runtime/helper caches may be warm, but this is not a persistent warm-worker
or cold-boot comparison. Setup discovery/spawn, proof-call, worker stages and
external verifier times are recorded separately. The validation worker may be
recycled before proving, so setup time is not a complete measure of the proof
worker's startup. All proofs require unchanged-verifier acceptance and the
three negative checks. Failures are retained, with no automatic retry or
selective exclusion.

Raw plans, telemetry and trial ledgers are saved under
`target/macos/benchmarks/<campaign-id>`, linked to source-bound worker runs.
Foundation thermal/low-power categories, `pmset` status, load averages and process
executable names are sampled before/after trials and about every ten seconds.
Nominal thermal state and low-power false can mean unknown/unsupported;
`pmset`'s absence of warnings is not a temperature measurement. Process CPU
percentages are decaying averages, not interval counters. No wattage or energy
measurement is made. Background applications and the default VM can affect times.

`--workload` selects `fibonacci`, `sha256-chain`, or `segment-boundary`. Inputs
and expected journals are calculated independently of receipts. SHA uses ten
hash iterations; the boundary fixture uses mode 1/parameter 8 and requires at
least five segments. `--po2` accepts 14..18, defaulting to 16 for boundary and 18
otherwise. Keep the tested boundary po2 16 because the pinned tiny-tail recursion
artifact limitation still applies. SHA coverage does not imply Keccak or all
other precompile coverage.

`--admission-pressure` is opt-in and requires `--proof-only`. It exercises
**logical in-flight reservation pressure**, using the actual WorkerPool admission
policy and live host observations. Small reservation handles fill the accounting
budget without allocating the represented memory. The next real proof request
must be refused with typed `HostMemoryShortage { attempted: false }`, no proof
sidecar or helper launch, and unchanged held reservations. Dropping the handles
must restore the ledger to zero; the following normal request must produce a
complete independently verified proof. The refusal is expected failure evidence,
not a proof. No physical host-memory exhaustion or RSS-limit kill is induced;
those remain unrun. The accepted SHA case held 107 one-GiB logical reservations,
refused the six-GiB proof budget before dispatch, dropped all reservations to
zero, and verified the recovery proof after the production path recycled the
warm worker. No 107-GiB physical allocation occurred.

The 4 KiB case stresses the supported staging boundary and synchronization with
a complete proof. It does not impose physical GPU-memory pressure. It permits
only 32 output digests per dispatch, compared with 4096 at the default 512 KiB,
so it creates many more command completions. The accepted run recorded exactly
16,680 and stayed within 4,096 bytes of logical staging. No speedup is claimed.
The multi-segment acceptance used the default budget to isolate these cases.

Per-request `resource.json` preserves owned process identity, before-request
RSS, periodic samples/peak, and idle RSS after independent verification and a
one-second settle interval. Compare warm-request baselines and
idle observations within one PID; distinguish cold initialization and any
recycle. The normal policy can recycle earlier for memory admission as well as
at the 20-proof periodic threshold; neither behavior was disabled. The accepted
twenty-request run used sixteen worker PIDs, with a longest same-PID success
streak of two. Report this as twenty consecutive accepted WorkerPool requests,
not twenty proofs in one long-lived worker. Request-body times had a 164.845-second
median and 157.222–166.442-second range; these are acceptance observations, not a
controlled comparison. RSS excludes helper/VM memory and unmeasured driver
allocations. This establishes bounded repeat/recovery evidence under the current
policy, not leak-free retention, physical host-pressure recovery or resident-limit
kill behavior. The fixed-setting comparison above is separate evidence; broader
benchmark and resource coverage remains open.
