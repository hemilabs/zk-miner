## What a Mac miner does with #37's features today (verified, not assumed)

- **Confinement:** `zkminer-prove-risc0/src/confinement.rs` is a no-op off Linux (`confine()` returns
  `Ok`, `is_confined()` false, no private TMPDIR). The Metal worker runs every guest unconfined, as
  before #37. `zkminer-witness-sandbox`, `-store`, `-broker`, `-builder` (wasmtime) and `-host` do
  **not build on macOS** (seccomp, Landlock, Linux `*at` syscalls; the builder and broker depend on the
  sandbox unconditionally). The macOS CLI does not link them (`cfg(target_os = "linux")` deps), so the
  kit is unaffected; they are excluded from the macOS test runs.
- **Witness jobs:** on macOS `run/witness/stub.rs` builds no runtime. `[witness] enabled = true` pages
  `WITNESS-DISABLED … served on Linux only` at start; every job whose `inputData` carries
  `WITNESS_JOB_TAG_V1` is recognised by the inline path (`is_witness_input` → `note_class`) and skipped
  before measurement or claim. So **a Mac miner never serves, measures or claims a witness job, and no
  requester witness guest runs on a Mac**. `zkminer witness init-store/self-test` and
  `zkminer artifact publish` bail ("Linux only"); `zkminer simulate --descriptor` uses
  `simulate_witness_stub.rs` (refuses).
- **The Metal worker and #37's new requests** (checked directly against the release worker with a
  temporary, uncommitted copy of #37's `tests/witness_prove.rs` pointed at the Metal binary,
  `logs/metal-witness-prove.log`): a witness `Prove` with a wrong journal hash answers
  `JournalDiverged` and proves nothing; a tampered W answers `InputMismatch`; retries reuse the one
  execution; a matching witness proves (32,768 cycles, Groth16, 54.8 s in that debug-built test) and
  the segment directory is emptied. `--witness-execute` (the sandboxed one-shot execute that returns
  `WitnessExecutePo2.sys_rand_draws`) exits 89 `Unsupported` ("no witness execute mode") on the Metal
  binary. So the Metal worker would handle a witness `Prove` correctly, unconfined, if a host sent
  one; the macOS miner does not.
- **Network guard (open issue 1):** see below. On macOS the guard refuses every public connection.

## Performance

The merge changes nothing in risc0 or the kernels. #37 changes what every proof does around them:
segments go to `~/.zkminer/risc0-segments/<pid>` instead of risc0's tempdir under `/var/folders` (the
same APFS volume), and the Groth16 call goes through `groth16_wrap::prove`, which on Metal is the same
`prove_with_opts(groth16)` call.

- Full `--benchmark`, default budget, first run (load 9.4 at start): 6 programs 174.44 s, 885.4K c/s
  (5 programs 174.18 s), +2.3 % against RC3's 170.56 s, above the 1.5 % threshold. So an A/B against
  `metal-3.1`'s worker was run (A = `metal-3.1` `6ca46df`, B = this branch; both `--release` through the
  mirror, A sha256 `692c2de8…`, B `14f81c33…`).
- **Interleaved `BENCH_ONLY=memory-merkle`, 7 pairs, default budget:** A STARK median 8.51 s
  [8.50-8.53], B 8.55 s [8.52-8.58]; per pair B-A +0.01 / +0.05 / +0.06 / +0.05 / +0.00 / +0.08 / +0.04 s
  (median +0.05 s, +0.6 %). Wraps 1.73-1.76 s on **both**; peaks 13.22 GB on both.
- **Full suite, A then B back to back:** A 172.93 s (893.1K c/s), B 173.53 s (890.1K c/s): **+0.35 %**.
  Every program within 0.5 %; wraps 1.74-1.76 s on both; peaks 14.01 / 14.02 GB; wall 258 / 259 s.
- So this machine is ~1.4 % slower today than at RC3 for the unchanged `metal-3.1` worker too (RC3's
  wraps were 1.58-1.61 s, today's 1.73-1.76 s for A and B alike). The merge's own cost is +0.3 to
  +0.6 %, consistent across pairs: likely the segment files' new location (`check_room`'s `statvfs` and
  emptying the directory per proof). Not acted on.

## Open issues (need the user's decision where marked)

1. **DECISION: #37's network guard refuses every public connection on macOS (and on Windows),** so a Mac
   miner on this branch **cannot download any job's ELF from a public store** (`zkminer-chain`'s ELF
   fetch goes through the guard). Measured: `a_real_elf_downloads_in_public_mode` fails with "could not
   ask the kernel how 140.211.167.122 is routed (unsupported)" (`logs/real-elf-download.log`). Two
   causes, both in `zkminer-netguard`: the per-destination route query (`routes.rs` `sys::query`) is
   implemented with netlink only and returns `Unsupported` elsewhere, and every admission asks it; and
   the near-hop probe's fallback check connection (`nearhop.rs` `confirm_once`) is Linux-only, while a
   2-hop probe on macOS times out instead of reporting EHOSTUNREACH (1.1.1.1:443 → `TimedOut`). The 6
   failing tests above are this. It is the same on `pr/37` alone. Mining in `[dev] private_network`
   mode (the localnet tests) works. Options: a macOS route oracle (`PF_ROUTE` `RTM_GET`) and a macOS
   check connection (security code to write and review); or a macOS policy that admits without the
   oracle (weaker than #37's design); or ship the beta with ELFs only from dev/private stores. Not
   changed here: it is #37's security design.
2. **Witness jobs on a Mac** (above): not served; recognised and skipped; `[witness] enabled` pages. No
   requester witness guest runs on a Mac. Inline jobs' guests run unconfined in the Metal worker, as
   before #37 (#37's confinement is Linux-only). Whether the beta should state that in its docs is the
   user's call; nothing was added.
3. **Linux/Windows not built or run here.** Only type-checked with stub compilers (above). Semantic fix
