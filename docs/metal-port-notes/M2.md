# M2: zk-miner host side for Metal

Item M2 of the risc0 Metal-port plan (`deps/risc0/docs/metal-port/PLAN.md`, section 3 row M2,
section 4.6, errata 8.6). Only `crates/zkminer-prover/src/{discovery,dispatcher,benchmark,memory}.rs`
changed. No `Cargo.toml`, nothing in `zkminer-prove-risc0` (that is M1).

## What was done

Each change copies how the code already handles `rocm`/`intel`. Every new path is either
`#[cfg(target_os = "macos")]` or only runs for `gpu_tag == "metal"`, so Linux behaviour is unchanged.

### discovery.rs
- `GPU_TAGS` is now `["cuda", "rocm", "intel", "metal", "generic"]`. `metal` is searched before
  `generic`, like the other vendor suffixes. `worker_binary_name("risc0", "metal")` returns
  `zkminer-prove-risc0-metal`.
- `infer_gpu_tag` maps a `-metal` suffix to `"metal"`. This is used for explicitly configured binaries.
- `detect_apple_gpus()` (macOS only) is called from `detect_all_gpus()`. It returns at most one
  `DetectedGpu { gpu_tag: "metal", device_index: 0, pci_bus_id: "apple-gpu0", name, compute_cap: None }`.
  - The name comes from `system_profiler SPDisplaysDataType -json`, run through the same bounded
    runner (`output_with_timeout_capturing_stdout`, `GPU_TOOL_TIMEOUT` = 5 s) as `nvidia-smi` and
    `rocm-smi`. The first entry whose vendor or model says Apple is used.
  - If that fails, the fallback is `sysctl machdep.cpu.brand_string`, but only when it starts with
    "Apple". An Intel Mac gets no entry.
  - The JSON parse is a separate pure function with unit tests.
- `APPLE_GPU_PSEUDO_BUS_ID = "apple-gpu0"`. It is stable and non-empty, and it contains no `:`, so
  `normalize_pci_bus_id` leaves it unchanged and it can never collide with a real bus id.
- SP1 is never expanded onto an Apple GPU. `sp1_serves_card("metal")` and `sp1_server_name("metal")`
  already return false/None, and a test now pins that.
- Pre-existing test fix: `the_sp1_server_checked_is_the_one_the_worker_will_run` failed on macOS
  before this item (`/var` vs `/private/var`, because the code under test canonicalizes). The test
  now canonicalizes its temp dir. The production code is unchanged.

### dispatcher.rs
- `physical_gpu_id`, `proving_gpu_count` and the two post-benchmark worker-recycle sites now include
  `"metal"` next to `cuda|rocm|intel`. Effects:
  - `risc0:metal:0` gets a per-GPU lock (`metal:0`).
  - It counts as one GPU toward the default `max_concurrent`.
  - Its worker is recycled after a benchmark to free unified memory.
- Device id: `gpu_device_id("metal", "0")` already returned `gpu-metal0` (tag-qualified form). Tests
  now pin it, along with `benchmark_device_id("risc0:metal:0")`.
- `gpu_vram_bytes("metal", Some(_), _)` returns `metal_vram_budget_bytes(mem_total)`, which is
  `hw.memsize − METAL_HOST_RESERVE_BYTES`. It returns `None` if that is not positive. With no device
  index (an explicit binary) it returns `None`, as for every vendor.
- `METAL_HOST_RESERVE_BYTES = 8 GiB` (a named public const). Why 8 GiB:
  - Unified memory means the GPU working set competes with the OS, WindowServer, the miner and the
    prover's own host-side state for the same pages.
  - 8 GiB matches Metal's own ceiling on this machine. `recommendedMaxWorkingSetSize` is 30.15 GB of
    38.65 GB (PLAN.md section 1, measured), and 36 GiB − 8 GiB = 30.06 GB.
  - It is larger than `DEFAULT_HOST_RESERVE_BYTES` (3 GiB). That reserve assumes the big buffers live
    on a discrete card.
- `gpu_env` has a new `"metal"` arm:
  - No `*_VISIBLE_DEVICES`, `CUDA_DEVICE_ORDER`, `ZE_*`, `ONEAPI_*`, `NVCC` or `HSA_*`.
  - It sets only `ZKMINER_CUDA_VRAM_BYTES` (`CUDA_VRAM_BYTES_ENV`) to the budget, and only for an
    enumerated device (`device_index.is_some()`), as for CUDA. An explicit binary gets an empty env.
  - The risc0 worker reads this variable in `release_groth16_cache_if_tight`. On this 36 GiB host it
    gets 30,064,771,072 bytes (≈28 GiB), which is above that function's 20 GiB threshold. Whether a
    unified-memory worker should keep the SRS cache is M1's decision.
- `read_card` / the VRAM admission gate has no metal reader: `read_drm_card_occupancy` returns
  `None` for `metal`, which means "no opinion", the same as an unreadable card. Admission on macOS is
  therefore done by the host-memory ledger (below) and the per-card lock.

### memory.rs
- `mem_total_bytes()` on macOS reads `sysctl hw.memsize` via `libc::sysctlbyname`. On Linux it reads
  `/proc/meminfo` as before (the code is behind `cfg(not(target_os = "macos"))`).
- `mem_available_bytes()` on macOS returns
  `(vm.page_free_count + vm.page_pageable_external_count + vm.page_purgeable_count) × vm.pagesize`,
  capped at `hw.memsize`. These are the free, file-backed (page cache) and purgeable pages: the macOS
  analogue of Linux `MemAvailable`, which also excludes anonymous memory.
  - `kern.memorystatus_level` was rejected. It read 90% on this host while anonymous pages held
    about 16 GB, because it counts memory the compressor could squeeze.
- New helpers `sysctl_u64` (accepts 32- or 64-bit values) and `sysctl_string`, macOS only and
  `pub(crate)`.
- `parse_meminfo_kb` has `cfg_attr(macos, allow(dead_code))`, so the macOS build adds no new
  warning.
- Ledger behaviour on macOS with a known `mem_total`:
  - Before this item, both figures were `None` on macOS. `reserve_host_memory` failed open (logged
    "cannot read host memory"), and `host_side_refusal`, `sp1_concurrent_capacity` and
    `worker_memory_ceiling_bytes` all took their `unwrap_or(u64::MAX)` / `?` paths.
  - Now both figures are known. `can_admit` (committed and live terms), `host_side_refusal`,
    `worker_memory_ceiling_bytes` (= total − 3 GiB) and the pressure state's free-memory floor all
    run on real numbers.
  - PSI (`memory_stall_percent`) stays `None` on macOS. `pressure_state` falls back to its
    free-memory floor by design.

### benchmark.rs
- `get_cpu_info()`: after the Linux `/proc/cpuinfo` block, the macOS block reads
  `machdep.cpu.brand_string` (e.g. "Apple M5 Max").
- `get_total_memory_bytes()`: on macOS it returns `memory::mem_total_bytes()` (`hw.memsize`).
- Consequence: on macOS the hardware fingerprint changes once. It used to be
  `Unknown CPU|N|0GiB|...` and now contains the real CPU name and RAM size. Any macOS benchmark cache
  written before this item is re-benchmarked once.

## Plan lines followed
- PLAN.md section 3 M2 row; section 4.6 M2; errata 8.6. The acceptance command uses the corrected
  form `cargo test -p zkminer-prover -- discovery:: dispatcher::`.
- PLAN.md section 1 device facts (`recommendedMaxWorkingSetSize` 30.15 GB) were used to choose the
  reserve.
- There is no CUDA source counterpart: this is host-side Rust. The patterns copied are the existing
  `rocm`/`intel` arms in the same files.

## Assumed, not verified
- Linux was not built or run. Its behaviour is unchanged by construction: every changed Linux-visible
  line only adds a `"metal"` alternative or an arm that `cuda|rocm|intel` keys never reach. The
  `/proc` paths are kept verbatim under `cfg(not(target_os = "macos"))`.
- A real `zkminer-prove-risc0-metal` worker was not spawned (M1 does not exist yet). Discovery
  expanding it into `risc0:metal:0` is covered by the code path shared with the other vendors and by
  the unit tests, not by an end-to-end run.
- The 8 GiB reserve is based on one machine (36 GiB). On a 16 GiB Mac the budget is 8 GiB, while
  Metal's own recommended working set there is about 10.7 GB, so this is conservative. It has not been
  measured on other sizes.

## Known gaps
- GPU power on macOS: `read_gpu_power_by_card` is Linux-only, so an Apple GPU row takes
  `FALLBACK_GPU_WATTS` (300 W). That is far above an M-series GPU's draw. No `powermetrics` reader
  was added because it needs root.
- `gpu_fingerprint` has no Apple entry. The CPU brand string, which is now in the fingerprint,
  already identifies the SoC.
- Per-process host RSS (`process_group_peak_bytes`, `current_host_bytes_for_slot`) still reads
  `/proc` and is `None` on macOS. The ledger treats a slot's resident memory as 0, which is the
  conservative reading.
- The VRAM admission gate has no unified-memory reader (it has no opinion on `metal`).
  `MTLDevice.currentAllocatedSize` is only visible from inside the worker.
