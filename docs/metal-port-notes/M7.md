# M7: hide the Groth16 first-wrap cost in the Metal worker

Item M7 (BASELINES.md section 6, open issue 1; Z10 open issue "start `prestart_prover()` earlier").
Branch `item/M7` of zk-miner (worktree `/Users/user/zkminer/zk-miner-wt-M7`, based on `metal` bf4ec2e).
It builds against the fork `deps/risc0` `zkminer/metal` d081b5937 (the wave-5 baseline). risc0 is not
edited.

Owned: `crates/zkminer-prove-risc0/**` (Metal paths), its tests, and this note.

## Summary

The Metal worker now starts building the Groth16 witness graph on a background thread as soon as it
starts. It does this in IPC mode before the command loop, in `--benchmark` before the pipeline warm-up,
and in `Warmup` right after the component install. Revert knob: `ZKMINER_G16_PRELOAD=0` (also `off` or
`false`).

**Result.** The first wrap of a worker process drops from 6.4-7.8 s to 2.8-2.9 s whenever about 5 s or
more pass between worker start and that wrap. Measured with `--benchmark` memory-merkle (wrap -3.70 s,
0/8 slower), at the 4 and 8 GiB budgets (-4.85 s and -4.04 s, 0/3 each), and on an IPC worker that idles
before its first short job (-2.28 s median).

**Costs.**
- First-job STARK time: no change (inside the A-vs-A spread in every A/B).
- Metal (GPU working-set) peaks: unchanged at every budget.
- Process footprint: unchanged on the production Prove path at 4 GiB, 8 GiB and the default budget.
- Process footprint where it rises: by 1.5-2.2 GB, in a process whose first proof is staged
  (`--benchmark`) or short and preceded by idle time. The graph, which risc0 keeps for the life of the
  process, is then resident during that first STARK. The worker's steady-state footprint (every proof
  after its first wrap) already included it, so the worker's lifetime peak does not change (details
  below).

**The proving key is not preloaded**, a decision made from measurements:
- Its load (0.13-0.55 s) already runs beside the 0.25-0.5 s witness.
- It was on the wrap's critical path for 3-87 ms in only 5 of 49 measured wraps.
- Holding it early would put 3.9 GB of device memory beside the STARK pools. Even the cache-keep rule
  (`keep_groth16_cache`) refuses that on this 28.1 GiB machine at po2 20.

## Profile before (baseline worker, A)

`BENCH_ONLY=fibonacci RISC0_VERBOSE=1 RUST_LOG=info,risc0_groth16=debug`, first wrap of the process
(`scratchpad/w5b/M7/prof1.log`):

```
groth16 witness graph prepared in 4730.6 ms (18148720 nodes)
[groth16-metal] pre_gpu done=4.5ms key loaded=118.3ms witness=3477.1ms gpu lock=3477.1ms proved=5336.5ms
[succinct_to_groth16] identity_p254=1480.2ms shrink_wrap=5337.4ms total=6817.5ms
```

- The first-wrap delay is the witness graph alone. `fast::preload` takes 4.7-5.3 s on one core:
  - read 250 MB;
  - sha256;
  - deserialize;
  - convert 18.1M nodes.

  It also holds ~2 GB of host memory (footprint `internal` 673 → 2801 MiB across the wrap).
- The key load (`metal_preload`, G10 mmap + compact cache) takes 118 ms and overlaps the witness.
- Where the graph is built today:
  - Staged proofs (`--benchmark`: composite, then `compress(succinct)`, then `compress(groth16)`):
    only at `prestart_prover()` inside `compress(groth16)`. Then identity_p254 runs (~1.1 s), and
    shrink_wrap waits ~3.5-4 s for the rest.
  - Production `prove_with_opts(groth16)`: the zkvm already spawns `preload_graph` when
    `prove_session_impl` starts (prover_impl.rs ~l.649), and once at prover construction. So a first
    job whose STARK + identity_p254 lasts more than ~5 s already hid it.
  - All of these share risc0's `OnceLock<Program>`: concurrent callers block on the one build, so an
    extra early call adds no work.

## Change

- `metal_host::start_groth16_graph_preload(at)`:
  - Runs once per process: an `AtomicBool`, reset if the thread cannot be spawned.
  - Spawns thread `g16-graph-preload`, which calls the public `risc0_groth16::prove::preload_graph()`
    and logs `Groth16 witness graph ready N s after the preload started at <site>`.
  - Refuses (and logs why) when `ZKMINER_G16_PRELOAD` is `0`/`off`/`false`, or when the
    `risc0-groth16` component is not installed yet. The second guard matters: risc0 caches a failed
    graph build for the life of the process (`OnceLock<Result<..>>`). A preload that ran before
    `Warmup` installed the component would therefore fail every wrap of that worker. Verified with
    `RISC0_GROTH16_DIR=<missing>`: the preload is refused and the wrap fails as before.
  - The pure decision `graph_preload_refusal` is unit-tested.
- `groth16_component::installed()`: whether the component is complete where `ensure_installed` looks.
  It checks `RISC0_GROTH16_DIR`, else `$RISC0_HOME`/`~/.risc0/extensions/v0.1.0-risc0-groth16`.
- `main.rs` call sites:
  - `--benchmark`: before the device line and `warm_up_pipelines`.
  - IPC: after the footprint guard, before `run_worker_loop`, unless the Mac is refused or the worker
    is measure-only (`measure_only_worker()`, factored out of `warm_up`).
  - `warm_up`: after `ensure_installed`, for a worker that started before the component existed.
- `tests/metal_worker.rs`: new ignored test `a_first_prove_without_warmup_proves` (an IPC Prove on a
  fresh worker). For the A/Bs it reads `ZKMINER_M7_WORKER` (binary), `ZKMINER_M7_FIB_ITERS` and
  `ZKMINER_M7_IDLE_MS`.

**Memory, stated plainly.**
- Device (Metal working-set) peaks are unchanged at 4 GiB, 8 GiB and the default.
- The process footprint is unchanged on the production Prove path at 4 GiB and 8 GiB (above).
- The process footprint rises by 0.9-2.2 GB in a process whose first proof is staged (`--benchmark`, the
  IPC Benchmark's first program), or short and preceded by idle time. The ~2 GB graph is then
  resident during the first STARK instead of arriving during the wrap.
- That is the footprint every later proof of the same worker already has, because risc0 never frees
  the graph. The wave-5 baseline full suite (A) shows it:
  - memory-merkle as the 5th program: `start 7393 MiB` with the graph resident, peak 17264 MiB;
  - B's lone first-job memory-merkle: 16358 MiB median.

  So the worker's lifetime peak, and with it the `host_peak_bytes` the dispatcher's admission uses
  (M6 #7), does not change. On a Mac where even that steady state does not fit, `ZKMINER_G16_PRELOAD=0`
  restores the old timing of the first proof only.

## Tried and rejected

- **Preloading the proving key at worker start**, even when the budget has room.
  - Across 49 B wraps the key load took 0.12-0.55 s. It finished before the witness in 44 of them, and
    in the other 5 it added 3-87 ms (only under GPU contention). The gain cannot exceed ~0.1 s, and only
    on the first wrap: this machine releases the key after every proof (`keep_groth16_cache` is false
    at 28.1 GiB and po2 20), so every later wrap reloads it beside the witness anyway.
  - Cost: 3.9 GB of device memory beside the STARK pools for the whole first job (G8/G10 moved the key
    load after `release_hal_buffers` for exactly this reason).
  - Not implemented, so there is no knob.
- **Calling `risc0_groth16::prove::preload_graph_background()`** instead of a thread of our own. It does
  the same thing, but it drops errors and gives no completion time. The worker's thread calls the same
  public `preload_graph()` and logs both.

## Knobs

- `ZKMINER_G16_PRELOAD=0|off|false`: do not start the graph build at worker start. The default is on.

## Open issues

1. **risc0 (groth16 owner): the graph build takes ~5 s on one core.** That is why a first wrap less
   than ~5 s after worker start still waits; see the fibonacci and short-IPC rows. Two options:
   - persist the converted `Program`, e.g. a validated cache file like G10's compact coefficients;
   - parallelise the 18M-node conversion and skip the sha256 when a cache validates.

   Either would make the preload finish during the pipeline warm-up. Not done: risc0 is not edited.
2. **risc0 (groth16 owner): no public "is the component installed" check.** `component::component_dir`
   is `pub(crate)`. The worker therefore re-derives the directory (`RISC0_GROTH16_DIR`, else
   `$RISC0_HOME`/`~/.risc0/extensions/v0.1.0-risc0-groth16`). risc0 also asks rzup first. If an rzup
   install lives somewhere else, `installed()` returns false: the preload is skipped (safe, no
   speed-up) and wraps behave as before.
3. **risc0: a failed graph build is cached for the life of the process.** The worker guards against
   this (it never preloads before the install), but any early caller elsewhere could poison the cache.
   A retrying `OnceLock` (cache only `Ok`) would remove the trap.
4. Measured on the 40-core M5 Max only, with the GPU shared with other agents. Not measured on a 16 GB
   Mac. The footprint argument above (steady state unchanged) is what bounds it there.
