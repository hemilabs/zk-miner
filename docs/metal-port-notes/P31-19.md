## 3. Startup check (read-only)

zkminer already checks the selector before claiming, so no new check was needed:
`reverify_risc0` -> `ChainClient::verify_proof_system(Risc0Groth16, risc0_seal_selector())`
(`zkminer-chain/src/deployment.rs`). It reads the adapter's status, its code and its
`nativeVerifier()`, then the verifier's code hash and `SELECTOR()` (all `eth_call` / `eth_getCode`). It
refuses with "verifier SELECTOR() is 0x73c457ba but zkminer's seals are prefixed 0xe71e6620 — every
proof would revert VerifierCallFailed". On a refusal it logs a `PAGE` line, and `risc0_claimable()`
stays false, so no risc0 job is claimed. Held locks are still recovered. The check is re-run
periodically. The override is resolved before the check, so the check always tests the prefix that
will actually be sent.

Against the live 743111 deployment, a 3.1 miner therefore refuses every risc0 claim (fail-loud) until
a 3.1 verifier is registered. No transaction was sent to any network.

Fix round 1 closed two holes this check left open; see section 14: a selector override that differs
from the linked risc0's (e.g. a stale 0x73c457ba) and a CLI/worker risc0 version skew.

## 6. The 4 GiB tier: keccak pipelines deferred under a tight limit (new knob)

**Profile.** At `RISC0_METAL_MAX_WORKING_SET_BYTES=4294967296`, both fibonacci and memory-merkle
proved and recursed, but the wrap failed:
`failed to load the groth16 proving key: Metal working-set budget exceeded: allocating 4235118872
bytes ... with 65110016 bytes already allocated would exceed the limit of 4294967296`.
risc0 3.1's v0.2.0 prover plans 4039 MiB, even with P31-12's `split_h`. The worker's process-wide
pipelines hold 62 MiB, and 4039 + 62 = 4101 MiB, which exceeds 4096. This is the "4 GiB headroom in
the worker" issue that P31-12 and P31-14 (open issue 1) routed here. Measured:

| variant (fibonacci, 4 GiB) | held after proof | wrap |
|---|---|---|
| as built (all pipelines at start) | 62.1 MiB | refused |
| `ZKMINER_METAL_PREWARM=0` | 61.9 MiB | refused (the M9 prewarm is not the cause) |
| keccak pipelines not built at start (experiment) | **45.9 MiB** | **verified** |

**Change.** `metal_host::warm_up_pipelines` gets the knob `ZKMINER_METAL_PREWARM_KECCAK=auto|on|off`
(default `auto`).
- Under `auto`, if the working-set limit is at least the Groth16 prover's planned footprint
  (`risc0_groth16_sys::metal_planned_bytes`, header-only) + 512 MiB, keccak builds in parallel as
  before. Default and 8 GiB budgets take exactly this path: there is no behaviour or timing change
  there (logs show `keccak 0.0-0.1 s`).
- Otherwise keccak runs after the other three. It is skipped when `allocated + planned + 32 MiB >
  limit` (32 MiB is twice the measured 16 MiB of keccak pipelines). In that case the first keccak
  proof builds the pipelines itself, through its binary archive.
- `on` restores wave 7's behaviour. Verified: with `on` at 4 GiB, the wrap is refused again.
- Fix round 1: while the prover's plan cannot be read (a host upgraded from 3.0 whose v0.2.0
  component is installed only by the first Warmup, after this decision is latched), `auto` assumes
  `GROTH16_PLAN_FALLBACK` = 4235118872 B (3.1's plan under a 4 GiB limit, its smallest) instead of
  building keccak. Before, such a 4 GiB host built keccak and then refused its warm-up wrap. Roomy
  limits are unchanged (unit test: unknown plan at 4 GiB is deferred, at 8 GiB built). An
  unrecognised knob value now logs a warning (`bogus` at 4 GiB: warned, treated as auto, wrap
  verified, `fix1/knob_bogus.log`).

The rule uses no core count or RAM fraction: it compares the measured prover plan with the measured
allocation. Unit test: `the_keccak_prewarm_yields_to_the_groth16_prover_under_a_tight_limit`. This
lowers peak memory; it never raises it.

**Limit (open issue).** Once a keccak proof has run at 4 GiB, the keccak pipelines exist for the
rest of the process and every later wrap is refused again. That is P31-14's known-fail for keccak at
4 GiB. The real fix is on the risc0 side (≥ 5 MiB more Groth16 headroom; P31-12 suggests the NTT
tables in `sorted`'s free tail). This item does not fix it. Under the Metal-safety rules, a tighter
idea would be to release the keccak pipelines after a keccak job, but risc0 has no API for that.

## 14. Fix round 1: closing the fail-loud holes

**Override that differs from the linked risc0's selector.** When `prover.risc0_groth16_selector`
was set, the override was both the prefix and the value checked against `SELECTOR()`. A stale
`0x73c457ba` (the previous default and the previous doc's example) therefore passed against the live
v3.0 verifier, and every 3.1 fulfil would revert after the claim. A stock verifier's `SELECTOR()` is
the digest of its own parameters, so a seal under any selector other than the linked risc0's cannot
verify. Now `risc0_selector_refusal` runs at startup: an override that differs from
`risc0_groth16_default_selector()` sets `RISC0_SELECTOR_REFUSAL`, and `reverify_risc0` then clears
the verified adapter and fails every time ("PAGE: risczero.groth16.v1 verification failed
(prover.risc0_groth16_selector 0x73c457ba differs from the linked risc0's selector 0xe71e6620 ...)
— NOT claiming risc0 jobs"). Held locks are still driven. `ZKMINER_RISC0_SELECTOR_OVERRIDE_UNSAFE=1`
acknowledges a deliberate override (it then logs a warning and claims). The localnet harness sets it
whenever its config carries an override (the 3.0 fixture replay). Unit test:
`a_stale_selector_override_refuses_risc0_claims`. `parse_seal_selector` also used to panic on an odd
length or a non-ASCII byte; it now refuses anything but 8 hex digits (tested).

**CLI/worker risc0 skew.** The selector comes from the CLI's risc0, the proof from a separate worker
binary, and the handshake compared only `protocol_version`, which was 12 in both trees. Worker
discovery searches `~/.zkminer/provers` before the exe's sibling, and this Mac's installed worker is
the frozen 3.0 build. Read directly from the binaries' HelloAck (`fix1/hello_probe.log`):
