# M6: macOS host hardening of zkminer-prover (review and fix)

Item M6 of the risc0 Metal-port plan (`deps/risc0/docs/metal-port/PLAN.md` 8.7 "wave-4 additions",
M1 note "M2 / M4 (host side)"). Branch `item/M6` of zk-miner (worktree
`/Users/user/zkminer/zk-miner-wt-M6`, based on `metal` 7469b2a, the M1 merge). Built against the
merged fork `deps/risc0` `zkminer/metal` 9827b70c4.

Owned: `crates/zkminer-prover/src/**` and its tests, and `crates/zkminer-prove-risc0/src/main.rs` for
the worker side. One out-of-ownership line: `crates/zkminer-cli/src/commands/run.rs` (see
Deviations).

## Summary

On macOS the miner could not stop a Metal worker it had started. Two independent causes, both fixed:
the pid identity check read `/proc` (every check answered "not ours"), and the worker was never put in
its own process group (the `setpgid` sat inside a Linux-only `pre_exec`), so even a correct check
would have refused to signal it. Both are why the 600 s watchdog "fired" during M1's 19-minute
benchmark without killing anything, and why 7 `worker_lifecycle` tests hung. With them fixed the
suite passes (19 passed, 2 ignored, ~20 s, no hangs).

The rest: the benchmark deadline now scales for Metal; the host sizes Mac jobs from the same table as
the worker (new `metal_sizing.rs`, compiled into both); the benchmark device row shows the Metal size;
the host reads a Mac worker's memory (`proc_pid_rusage`); Mac workers get a footprint ceiling they
enforce on themselves and exit when the dispatcher dies.

Most important open finding (not in owned files): for any proof, at any po2 or budget, the Metal
worker's process footprint is about 8.5 GB larger than its GPU allocations. A trivial proof peaks at
15.9 GB of footprint under an 8 GiB budget. As the fork stands, a 16 GB Mac (minimum tier) cannot
run the worker. Details are under Measurements.

## What was fixed, file by file
- `zkminer-prover/src/memory.rs`: `ProcIdentity` + `proc_identity` (Linux `/proc`, macOS
  `proc_pidinfo`). `pid_starttime` / `pid_is_our_worker` go through it. The start-time unit is
  platform-specific and only compared for equality. macOS `anon_memory_of_pid`, `Footprint`,
  `macos_group_footprint`, `macos_pid_footprint`, and a macOS branch in `process_group_peak_bytes`.
  Linux-only tests are `cfg`-gated.
- `zkminer-prover/src/worker.rs`: `process_group(0)` off Linux. The macOS footprint ceiling goes in
  the spawn env. No `busctl` on macOS. `macos_live_group_members`.
- `zkminer-prover/src/metal_sizing.rs` (new, std only): `job_po2_for_limit`, `stark_peak_bytes`,
  `parse_bytes` (the fork's grammar), `host_working_set_limit` / `working_set_limit_of`,
  `WORKER_MAX_FOOTPRINT_ENV`, `FOOTPRINT_EXIT_CODE`, and unit tests.
- `zkminer-prover/src/benchmark.rs`: `risc0_slot_job_po2`, `is_metal_device_id`, `metal_job_po2`,
  and the Metal device row.
- `zkminer-prover/src/dispatcher.rs`: `METAL_BENCHMARK_CORE_SECS`, `metal_benchmark_timeout`, and
  `WorkerPool::benchmark_timeout_for`, used at all 8 benchmark/calibration deadline sites (watchdogs
  and card-guard waits).
- `zkminer-prover/src/discovery.rs`: `apple_gpu_cores()` (from `sppci_cores`, recorded at discovery)
  and a test.
- `zkminer-prover/tests/{worker_lifecycle,orphan_reaping}.rs`: see #11.
- `zkminer-prove-risc0/src/main.rs`: `#[path]` include of `metal_sizing` on macOS. Default po2 and
  the above-default warning come from the shared table. Inline `mac_footprint` module: footprint
  ceiling, orphan exit, per-phase peak footprint, and a `task_vm_info` breakdown (internal /
  compressed / graphics / resident) logged after each phase. Per-phase footprint peaks are logged

- `zkminer-cli/src/commands/run.rs`: one call site now calls `risc0_slot_job_po2(device, ..)`.

Reading:
- About **8.2 GB of "graphics" memory is charged to the process during the first rv32im segment
  proof, regardless of po2 or budget**. It is outside `currentAllocatedSize` (342 MiB), so the
  fork's working-set budget neither sees nor limits it. Recursion adds ~1.4 GB more.
- After the wrap, ~4 GB of internal (heap) memory stays held: the Groth16 host side, freed memory
  the allocator keeps, or both.
- Hypothesis, not verified: the driver's per-thread private (stack/spill) memory for the huge
  translated kernels, sized for full occupancy. It appears at first dispatch, not at PSO creation
  (start = 175 MiB after `warm_up_pipelines`). `footprint` and `vmmap` hang on this machine without
  task-port authorization, so no per-region breakdown was possible.
- Consequence: on a 16 GB Mac a trivial proof needs ~16 GB of footprint against 16 GB of RAM. See
  open issue A.

## Assumed, not verified
- The macOS kill paths were exercised with the mock worker (watchdog, warm-up deadline, preemption,
  close) and by the identity and group tests. A real Metal worker was not killed mid-proof by a
  watchdog in this item.
- `metal_benchmark_timeout` is calibrated from one machine (32 cores, po2 20). The 1.5×-per-step
  factor comes from a 4090 measurement, and the core scaling is linear by assumption. Not measured
  on a 7-10 core Mac.
- The footprint ceiling (`total − 3 GiB`) and the parent watch have not been run on a 16 GB or
  24 GB Mac.
- Host sizing assumes the worker's `recommendedMaxWorkingSetSize` is never the smallest term
  (true when RAM − 8 GiB < 0.75 × RAM below 32 GiB, and both ≥ 20 GiB above). The host cannot read
  that figure without Metal.
- `proc_pidinfo` answers nothing for a zombie on macOS, so `pid_is_our_worker` refuses to signal an
  unreaped exited worker. That is the safe direction (signalling a zombie is a no-op anyway).

## Deviations
- `crates/zkminer-cli/src/commands/run.rs` (not owned): one call changed from `risc0_job_po2(over,
  row, vram)` to `risc0_slot_job_po2(device, over, row, vram)`. The host's per-slot size is computed
  there, and goal 3 (one table for host and worker) cannot be met without passing the device. No
  other wave-4 item owns zkminer-cli.
- New file `crates/zkminer-prover/src/metal_sizing.rs`, inside the owned `src/**`. It is also
  compiled into the worker via `#[path]`, because the worker does not depend on `zkminer-prover`
  and the protocol crate is not owned. A later item may move it into `zkminer-prover-protocol`.
- `zkminer benchmark` ran with `HOME` set to a scratch directory (worker "installed" in its
  `.zkminer/provers`, `.risc0` symlinked to the real one), so it did not overwrite M4's installed
  worker or the user's benchmark cache.
