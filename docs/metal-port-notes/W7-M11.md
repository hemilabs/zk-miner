## 1. Protocol and power state

### Protocol (v12) and compatibility

- `PROTOCOL_VERSION` is now 12. `BenchmarkEntry` gains a last field, `power_state: Option<BenchPowerState>`:
  - `low_power_mode: Option<bool>`, `on_battery: Option<bool>`, `thermal: Option<u8>` (0 nominal .. 3
    critical);
  - `reduced()` names Low Power Mode, battery, and thermal serious or critical (fair is normal under load);
  - `merge()` keeps the worse of two readings.
- The codec is positional bincode, as at v4, so `#[serde(default)]` gives no wire compatibility. The bump is
  what turns a stale worker into a clean handshake refusal. Tests in `codec.rs`:
  - `a_benchmark_entry_carries_its_power_state`: every shape round-trips (`None`, all-unknown, full,
    reduced), in progress and result frames, and no field shifts;
  - `a_v11_benchmark_entry_does_not_decode_as_v12_but_its_hello_does`:
    - a hand-built v11 entry fails to decode, alone and as a last-program `BenchmarkProgress` frame, so it
      is refused, never misread;
    - a v11 `HelloAck` still decodes (`protocol_version` 11), which is what lets `worker.rs` refuse it at the
      handshake;
  - `the_worse_power_reading_wins`.
- Worker (risc0 Metal): each entry carries M9's reading (`metal_start::power_state().to_bench()`), merged
  from one read before and one after the program, and a warning is logged when it is reduced. Non-Mac
  workers and `ZKMINER_POWER_STATE_IN_BENCH=0` send `None`. The SP1 and OpenVM workers construct `None`
  (one line each; see deviations).
- End to end (`ipc/bench_ipc.py`): it drives the real worker over IPC (Hello v12, Benchmark with
  `BENCH_ONLY=fibonacci`) and decodes the frames by hand.
  - It received `HelloAck protocol 12` and `power_state {'low_power_mode': False, 'on_battery': False,
    'thermal': 0}` in both the progress frame and the result frame, with all 91 bytes consumed.
  - With the knob set it received `power_state: None`.

### Pricing rule: price as measured, re-benchmark on the operator's command, no discount

- `benchmark::build_gpu_device_benchmarks_from_workers` stores the reason on each `ProgramStage`
  (`power_reduced`, JSON only, `#[serde(default, skip_serializing_if = "Option::is_none")]`).
  `DeviceBenchmark::power_reduced()` aggregates it. No `DeviceBenchmark` or `BenchmarkSuite` field was
  added, so no other crate changes.
- **The rule.** A suite with a marked row stays in use and is priced as measured, at every start, whatever
  its marks. A throttled row under-states the Mac, so it only claims less and never over-promises a
  deadline. The cache is never dropped or rewritten for its marks.
- **Re-benchmark advice** (`power_redo_reason`, returned by the new
  `load_cached_benchmark_with_advice()` and logged as a WARN by every load): given when a row carries a
  **redo cause** (`power_redo_cause`: only Low Power Mode and battery) and the host is at full power at
  load (every known field full, which also means not hot: a benchmark on a hot Mac would measure the heat).
  The advice names the commands: `[b]` on the Benchmark screen, or `zkminer benchmark`. Their full-power
  result replaces the suite when saved, and the advice stops.
- **Why not a redo at load (fix round 2, review finding).** The first round and fix round 1 dropped the
  cache (returned `None`) to "redo" it. But no caller benchmarks on `None`: `zkminer run` has had auto-benchmark at startup
  disabled since before this item (GPU proving in passthrough VMs freezes the host; run.rs "press [b]"),
  `spawn_streaming_benchmark` has no call site, and `zkminer mock` behaves the same. So a "redo" threw away
  the measured suite for that start, priced from `synthetic_conservative_benchmark` placeholders (or
  claimed nothing with the gate on), and used up fix round 1's one-shot record, after which the reduced suite
  stayed for good. Fix round 1's tests passed only because their `start()` helper benchmarked on `None`, a
  caller that does not exist. Starting a benchmark from the miner would need run.rs, which this item does
  not own, and would re-enable what was disabled on purpose. So the record
  (`SavedBenchmark::power_redo_attempted`) is removed and the load is read-only; a fix-round-1 cache that has
  the key still loads (serde ignores it; tested).
- **Thermal** (fix round 1, review finding): a thermal mark (`thermal serious`/`critical`) stays on the
  row for the record but never asks for a re-benchmark. The worker keeps the worse of a reading before and
  one after each program, and the after-reading comes at the end of minutes of GPU load: a fanless Mac
  heats itself to `serious` while benchmarking, and a re-benchmark on a cool start is marked again.
  Sustained-load thermal is the speed the Mac really mines at.
- Since nothing re-benchmarks by itself, no loop is possible (the first round's) and no one-shot bound
  is needed (fix round 1's). The load also no longer writes `benchmarks.json`, which removes fix round 1's race with a
  concurrent `[b]` save.
- Why not a discount: it would need a measured slowdown factor per state, and none could be measured here
  (a Mac Studio on mains power; Low Power Mode needs sudo).
- Tests (`benchmark::power_state_tests`, independent of the environment knob; each cache test uses its
  own temp directory; the start helper is shaped like the real callers: price from what the load
  returns, never benchmark on `None`):
  - marking per program and per row;
  - the advice decision in every state (full, desktop with no battery reading, still reduced, hot,
    unknown, knob, unmarked), and that it names `[b]` and `zkminer benchmark`;
  - `a_reduced_suite_stays_in_use_until_the_operator_rebenchmarks`: a battery suite on battery (in use,
    no advice), five full-power starts (the measured battery suite in use every time, advice every time),
    a hot start (in use, no advice), the cache file byte-identical after all loads; an operator full-power
    save (clean suite in use, no advice); a re-marked operator save (in use, advice); the knob (in use,
    no advice);
  - `a_self_heated_benchmark_is_never_redone`: a `thermal serious` row over five cool starts and a hot
    one: in use, no advice;
  - `a_read_only_cache_still_loads_with_advice`: the load needs no write;
  - the mark surviving save and load; an older cache, and a fix-round-1 cache with `power_redo_attempted`,
    still loading.
  - Reproduction kept in the log: a caller-shaped start against fix round 1's code dropped the measured
    battery suite at the first full-power start
    (`scratch/w7/W7-M11/fix2/repro-before-fix.log`: "a start at full power dropped the measured suite").
- `discovery::this_macs_power_state_answers_and_is_full`: the probes answer on this Mac.

## 2. Tier moves and the footprint model

### The rule

`metal_sizing::job_po2_in(limit, table, ram)` is `min(GPU rule, footprint cap)`, where:
- the footprint cap is the largest po2 whose full-suite footprint (`footprint_bytes`) leaves
  `FOOTPRINT_RESERVE_BYTES` = 4.5 GiB of RAM (a fixed amount, not a fraction: PLAN 9.1);
- RAM is `hw.memsize` (read through std's libSystem, so the file stays std-only), or
  `ZKMINER_METAL_HOST_RAM_BYTES` for simulations;
- it only removes rows above M8's. M8's rows are shipped and measured, and an unknown RAM keeps M8's.

Host and worker read the same file, so the claim size, the benchmark row and the worker's default segment
size agree.

| table (`ZKMINER_METAL_TIER_TABLE`) | GPU rule | ceiling (`min_limit_for_po2`) | footprints |
|---|---|---|---|
| `m8` | < 6 GiB 18, < 12 GiB 19, else 20 | 18 from 4, 19 from 6, 20 from 10 GiB | not used |
| `w7` (**default**) | < 6 GiB 18, < 10 GiB 19, else 20 | M8's | merged risc0 |
| `r2` (opt-in; needs W7-A1, R2, G1) | < 8 GiB 19, else 20 | 19 from 4, 20 from 8 GiB (R2: not below the tier budget) | combined risc0 + `MallocLargeCache=0` |

`ZKMINER_METAL_PO2_TABLE=m1` still restores M1's table and wins over the tier knob.

### Footprint model (full six-program suite, `/usr/bin/time -l` peak, worst over the budgets the size is tiered at)

| po2 | merged risc0 (w7) | combined + `MallocLargeCache=0` (r2) |
|---|---|---|
| ≤ 18 | 7.5 GiB (M8: 7.31 GiB at 4 GiB) | 6 GiB (`fullC/X4`: 5.94 GiB at 4 GiB) |
| 19 | 10.5 GiB (`full10/A`: **10.45** GiB at 10 GiB) | 7 GiB (`fullC/M4`: 6.20 GiB at 4 GiB; `fullC/M8w19`: 6.82 GiB at a 16 GB Mac's 10.67 GiB HAL limit with an 8 GiB plan) |
| 20 | 16.25 GiB (`full10/B`: **16.18** GiB at 10 GiB) | 12 GiB (`fullC`: M8 10.63 at 8 GiB, M16real 11.07 at 10.67 / 8, **M10 11.86** at 10 GiB, M12f 11.04 at a 12 GiB HAL with a 10 GiB plan) |

At po2 20 the big programs' segment phase is the peak. On the merged build that is 16.5 GB of footprint
against 9.5 GB of Metal allocations: about 7 GB of host state during segments (`full10/B.err`,
sha256-chain / ecdsa / bigint / chacha). A1 + R2 bring it to 14.66 GB with the large cache on (`fullC/R10`,
13.65 GiB), and G1's graph release (`MallocLargeCache=0`) to 12.74 GB (11.86 GiB).

|---|---|---|---|
| 16 GB, idle 8 GiB | 19 | 19 | 19 (po2 20 needs 12 + 4.5 > 16 GiB) |
| 16 / 18 GB, owner-active 4 GiB | 18 | 18 | **19** (7 + 4.5 ≤ 16) |
| 18 GB, idle 10 GiB | 19 | 19 (po2 20 needs 16.25 + 4.5 > 18 GiB) | **20** (12 + 4.5 ≤ 18) |
| 24 GB, idle 16 / active 8 GiB | 20 / 19 | 20 / 19 | 20 / **20** |
| ≥ 32 GB | 20 | 20 | 20 |
| any Mac ≥ 20.75 GiB RAM under a 10-12 GiB budget | 19 | **20** | 20 |

`w7` decides as `m8` on every real Mac's idle tier (pinned by
`the_w7_tiers_follow_the_gpu_rule_and_the_footprint_model`). It differs only under an explicit 10-12 GiB
budget on a Mac with at least 20.75 GiB of RAM, where po2 20 was measured −13 % STARK at +5.0 GB of
footprint, which such a Mac holds.

With `r2`, the dispatcher spawns Metal workers whose figure is below 20 GiB with `MallocLargeCache=0`,
unless the operator set the variable (`metal_sizing::spawn_without_malloc_large_cache`). The r2 footprints
assume G1's graph release, which needs the cache off from process start. A hand-run `--benchmark` under
`r2` should set it as well.

## 3. AOT packaging

- `scripts/mac/install-metal-aot.sh <set> <installed worker> [validated arch ...]`:
  - asks the worker for this Mac's GPU family (new `--metal-arch` flag: `MTLDevice.architecture.name`,
    `applegpu_g17s` here);
  - copies only that family's `*.binarchive` files (11 files, 165 MiB of the 1.7 GB set), each checked
    against `SHA256SUMS`, plus the family's `manifest.jsonl` lines. The checksum line is found by an exact

## 4. Image-id pass-through

`run_proof` binds the ELF to the job's programId through `verify_program_id`, which computes the image id.
`run_proof_once` used to compute it again, per attempt, before `receipt.verify`. It now receives the bound
id (`verify_image_id`; `ZKMINER_RISC0_RECOMPUTE_IMAGE_ID=1` recomputes it). Same ELF bytes, same digest:
`the_image_id_passed_through_is_the_recomputed_one` asserts equality.

The recomputation it removes costs 9.55 ms (fibonacci), 8.61 ms (sha256-chain) and 7.19 ms (memory-merkle)
per proof attempt (`gates/worker1.log`). That time comes after the STARK and wrap, so it is in the job's
latency but not in STARK time. The benchmark path verifies its own receipt and is unchanged.

## Knobs

- `ZKMINER_POWER_STATE_IN_BENCH=0`: the worker sends no power state, and the host ignores marks (no
  advice). Pricing is as measured either way.
- `ZKMINER_METAL_TIER_TABLE=m8 | w7 | r2`: M8's table; the default; the R2 rows (opt-in until W7-A1/R2/G1
  merge). `r2` also makes the dispatcher spawn Metal workers below 20 GiB with `MallocLargeCache=0`.
- `ZKMINER_METAL_PO2_TABLE=m1`: M1's table (unchanged, wins).
- `ZKMINER_METAL_HOST_RAM_BYTES`: the RAM the footprint model sees (simulation and tests).
- `ZKMINER_METAL_AOT=0`: do not point `RISC0_METAL_AOT_DIR` at the packaged archives.
- `ZKMINER_RISC0_RECOMPUTE_IMAGE_ID=1`: recompute the image id per proof attempt.

## Tried and rejected

- **po2 20 on an 18 GB Mac with the merged risc0 (the brief's main tier move)**: −13 % STARK on
  memory-merkle and −10 % on the full suite, but the full-suite footprint is 16.18 GiB against the 13.5 GiB
  allowed. Kept behind `r2`, where it fits.
- **po2 20 at 8 GiB on a 16 GB Mac (W7-R2's recommendation)**, in both builds:
  - merged risc0: R2 is needed even to prove it;
  - combined risc0 without MLC0: 12.42 GiB, over the 11.5 GiB allowed;
  - combined with MLC0: 10.63-11.07 GiB, under the bound but inside the worst-case model (12 GiB) and with
    0.43 GiB of margin at the realistic HAL limit.
- **Discount pricing**: no measured slowdown factor exists for Low Power Mode, battery or thermal states.
  Pricing as measured uses only measured rates.
- **Dropping the cache at load to force a redo, bounded by a one-shot record** (fix round 1's bound): no
  caller benchmarks on a missing cache, so it priced one start from placeholders and then kept the
  reduced suite for good (review finding of fix round 2, reproduced by a caller-shaped test).
- **Thermal as a redo cause, and an unbounded redo** (the first round's rule): a self-heating Mac loops,
  one full suite lost per start (review finding, reproduced by the tests above). Also considered: use only
  the before-reading of the first program. Rejected: it needs the worker to send two readings (a protocol
  change), and a Mac already warm from other work at the first program would still be redone into the
  same mark; the one-redo record would bound it, but it adds nothing over not redoing on thermal.
- **Copying every family's archives**: 1.7 GB, of which nine families are unvalidated (W7-Z1). Only the
  validated family of this Mac is installed.

## Deviations from the brief

- The brief's default `ZKMINER_METAL_TIER_TABLE` revert (`m8`) is in place. The new rows that need unmerged
  risc0 work are opt-in (`r2`), not default, as its validation rules require. The default `w7` decides as
  M8 on every real Mac, because the merged risc0's po2 20 footprint does not fit an 18 GB Mac.
- Files outside the owned list, each needed to compile or install:
  - `crates/zkminer-prove-sp1/src/main.rs` and `crates/zkminer-prove-openvm/src/main.rs`: one
    `power_state: None` line each, the new protocol field. sp1's build script does not run on this Mac
    (pre-existing; it needs CUDA) and openvm is excluded from the workspace, so both edits are compile-unchecked.
  - `Makefile.mac` and the new `scripts/mac/install-metal-aot.sh`: the worker's install path, which the brief
    lists as owned ("install/packaging scripts for the worker").
- `discovery.rs` gained `host_power_state()` and a thermal-state probe, which the pricing rule needs.
