## What was done

### `Makefile.mac` (new)
Run as `make -f Makefile.mac <target>`. The default target is `help`. GNU make 3.81 (the macOS one)
has no `.ONESHELL`, so each recipe is a single shell line that starts with a shared prefix:
- It checks that `ENV_SH` exists and sources it. This happens before `set -eo pipefail`, because
  env.sh's last line is a conditional export that returns 1 when the C++ toolchain is absent.
- It refuses to run if `RISC0_SKIP_BUILD` is set.
- It exports `NVCC=off HIPCC=off CARGO_BUILD_JOBS=$(JOBS)`.

Settings:
- Paths come from the layout that `Cargo.toml`'s `[patch.crates-io]` already requires:
  `ZKMINER_ROOT` = the parent of the Makefile's directory, `ENV_SH=$(ZKMINER_ROOT)/env.sh`,
  `RISC0_DIR=$(ZKMINER_ROOT)/deps/risc0`. This works from a worktree too.
- `PROVERS_DIR` defaults to `~/.zkminer/provers`.
- `JOBS` is `$CARGO_BUILD_JOBS` if set, else `hw.perflevel0.physicalcpu`, with a floor of 4. No core
  count is hard-coded (PLAN 9.1). It resolves to 6 here.
- Every cargo call passes `--locked`, because the README forbids `cargo update`.

Targets:
- `mac-prereqs` (also run by `mac-check`) checks:
  - The worker's own refusal rules (M1 `metal_host::support`): Darwin, arm64, not Rosetta,
    `hw.memsize` ≥ 12 GiB.
  - env.sh, `xcrun --sdk macosx metal --version`, cargo, the rzup Rust toolchain, the C++
    archiver (warning only), the risc0-groth16 component (warning only: the worker downloads it),
    and that Docker is not needed.
  - The fork checkout and its branch/HEAD.
- `mac-check` = `mac-prereqs`, then `cargo check` of `zkminer-prove-risc0 --features metal --bin
  zkminer-prove-risc0-metal` and of `zkminer-cli`.
- `mac-test-risc0` = `mac-test-risc0-{zkp,rv32im,recursion,keccak,groth16}`. These are the PLAN 2.10
  suites, run in `RISC0_DIR` under the default parallel harness:
  - `risc0-zkp --lib -- hal::metal`
  - `risc0-circuit-rv32im --lib -- prove::`
  - `risc0-circuit-recursion --lib`
  - `risc0-circuit-keccak --release --lib`
  - `risc0-groth16-sys --lib` + `risc0-groth16 --lib`

  Each unit is its own target, so each run stays under 10 minutes and the targets can be called
  one at a time. The zkvm e2e suites are not included: `host::recursion::tests` alone takes 1547 s
  (C9).
- `mac-test-miner` runs:
  - the worker's unit tests (`--release --features metal --bin zkminer-prove-risc0-metal`)
  - `zkminer-prover --lib -- discovery:: dispatcher::` (PLAN 8.6 form)
  - M1's real-worker IPC test (`--test metal_worker -- --ignored`: Capabilities, Warmup with a
    verified Groth16 proof, one Prove). `MINER_IPC=0` skips this one.
- `mac-build-worker`: `cargo build --release -j $(JOBS)` of the Metal worker and the CLI.
- `mac-install-worker` (depends on build):
  - Copies the worker to a temporary file in `PROVERS_DIR`, then renames it over the old binary.
    This way a running worker is never modified in place: macOS kills a process whose signed
    binary changes under it.
  - With `WARM=1` (the default), it then runs the installed binary once with `BENCH_ONLY=fibonacci
    --benchmark`. That builds all four circuits' PSOs (M1 `warm_up_pipelines`) and proves and
    verifies one Groth16 proof, so the OS shader cache and the keccak archive are filled at install
    time (PLAN 9.1, K5/M1 hand-off).
- `mac-bench` (depends on build): the built worker's `--benchmark`, passing `BENCH_ONLY` through.

## Dispositions of issues addressed to M4
- **M3** ("document the C++ guest toolchain (`rzup install cpp`) and the
  `AR_riscv32im_risc0_zkvm_elf` export"): **done**. README Prerequisites and env.sh; `mac-prereqs`
  checks it. The export already lives in `env.sh`.
- **M1 "K5 / packaging (M4/M5): ship or pre-build the pipelines at install"**: **done** with
  `mac-install-worker` (`WARM=1`, the default). M1's open point "cold pipeline build not observed"
  is now measured (242 s, above). Shipping prebuilt binary archives is not possible across
  machines (the K5 key includes the device and OS build).
- **M1 "M2 / M4 (host side)"**: risc0_job_po2 vs the table, the 600 s benchmark timeout, the
  `/proc` pid identity check, the device row, and macOS memory capping were all **fixed by M6**
  (`item/M6`, unmerged at the time of writing; M6 note, dispositions). GPU power (300 W fallback) is
  **not addressed** by anyone; it is listed in the README's known limitations and carried to M5 /
  wave 5.
- **PLAN 8.7 "worker_lifecycle tests fail/hang on macOS (M4 investigates and documents)"**:
  **root-caused by M6** (M6 findings 1, 2, 11):
  - `pid_is_our_worker` read `/proc`, so no identity-checked kill ever ran on macOS.
  - The worker's `setpgid` was inside a Linux-only `pre_exec`, so the worker shared the miner's
    process group and `kill(-pid)` hit nothing.
  - The `/dev/shm` SP1 test is Linux-only.

  M6 reports 19 passed / 2 ignored in ~20 s on its branch, twice under the default harness and
  once under each budget. Not reproduced here: these tests hang on the base this branch is built
  on. For that reason `mac-test-miner` does not include `worker_lifecycle` / `orphan_reaping` yet
  (issue 4).
- **M6 issue D** (mention `ZKMINER_WORKER_MAX_FOOTPRINT_BYTES` and the scaled Metal benchmark
  deadline): **deferred until M6 merges**. The README documents the branch it ships on, and these
  do not exist on `metal` yet. Text to add to the knob table once M6 is in:
  "`ZKMINER_WORKER_MAX_FOOTPRINT_BYTES` | Set by the miner for each Mac worker (`hw.memsize` − 3 GiB);
  the worker exits (status 137) when its process footprint passes it. `0` disables it." Also add a
  sentence under Known limitations: "the miner scales a Mac's benchmark deadline with its GPU core
  count and po2".
- **M6 issue E** (M6's `cp` briefly overwrote the installed worker at ~00:09-00:10 while an M4 run
  was using it). That run was M4's cold warm-up measurement (started 00:09:48). It finished
  normally: the proof was verified and the binary bytes were restored identical. No rerun needed.

## Issues for later items
1. **Z8 (zkp review, wave 4)**: under `RISC0_METAL_MAX_WORKING_SET_BYTES=4294967296` and the default
   parallel harness, the zkp suite has two failures:
   - `z6_poly_group_no_coeffs_spill` fails only because other tests' allocations overlap with it.
     It needs the crate's test lock (PLAN 8.7 isolation rule).
   - `ntt_commit_coeffs_lde_lg_10_20` (lg 20 x 211) cannot fit 4 GiB by construction. It should
     assert the clean budget error (as G7's tests do) instead of failing.
2. **G8 (groth16 review, wave 4)**: `risc0-groth16-sys --lib` under an 8 GiB budget and the parallel
   harness fails 4 MSM tests in some runs (8.68 GB already allocated by a concurrent key-loading
   test). These tests need a shared poison-tolerant GPU test lock (PLAN 8.7). G7 ran its budget
   runs with `--test-threads=1`, which hid this.
3. **M1 file owner / M5**: under a 4 GiB budget the worker's Warmup fails (as `Internal`), so a
   minimum-tier Mac with an owner-active budget takes no jobs at all. That is correct today, since
   the wrap cannot fit. However, the error kind should be ResourceExhausted, consistent with Prove.
   G10's compact coefficients / zkey mmap are the real fix.
4. **Whoever merges M6 (or M5)**: once M6 is on `metal`, add
   `cargo test --locked -p zkminer-prover --features testing --test worker_lifecycle --test
   orphan_reaping` to `mac-test-miner` (M6: ~20 s) and apply the README text from the M6 issue D
   disposition above.
5. **Wave 5 (C11/Z10, G9-G11, K7)**: the cold pipeline build is 242 s here, spread as
   rv32im+zkp 242 s, groth16 188 s, recursion 108 s, keccak 59 s. Only keccak has a binary archive
   (K5). rv32im/zkp and groth16 dominate and rely on the OS shader cache alone, which K5 saw miss.
   Extending K5's `ArchivedKernels` to them would bound the first-start cost after a cache
   eviction.
6. **M5 (baseline)**: `make -f Makefile.mac mac-bench` is the benchmark entry point. The full suite
   takes ~19 min, so run it in pieces with `BENCH_ONLY=<program>` if a 10-minute command limit
   applies.
7. **R17**: the README documents `RISC0_METAL_RV32IM_GPU_PHASES=witgen` as off by default and for
   debugging only. Update that row when R17 re-enables GPU witgen.
