Branch `item/B9-M26` (worktree `/Users/user/zkminer/zk-miner-3.1-wt-B9-M26`), from `item/B9-PKG` `f6b6eed`.
User decision 2026-11-17: the beta must support macOS 26 Tahoe as well as 27. This item lowers the kit's
minimum from 27.0 (B9-PKG) to **26.0**, validates the 26.0-target kernels on this Mac, pins the Metal

## 1. Kernels and binaries for 26.0

- **How:** as B9-PKG did for 27.0, with 26.0: `-C strip=none -C link-arg=-Wl,-S -C
  link-arg=-mmacosx-version-min=26.0` for the top-level cargo, `METAL_TC=target/macos-kit/metal-tc-26.0`
  whose `metal` adds `-mmacosx-version-min=26.0` and whose `--version` reads
  `Apple metal version 32023.922 (metalfe-32023.922.4) [-mmacosx-version-min=26.0]`.
- **Result** (`check-macos-release.sh --binaries 26.0`): worker and CLI `minos 26.0`, 7 metallibs for 26.0.
- **Metal language / AIR per target** (test kernel and all 175 kernel TUs; language always MSL 3.2,
  `!{"Metal", i32 3, i32 2, i32 0}`):

| target | 27B47 (Xcode 27.2, metal 32023.922) | 17F109 (Xcode 26.5, metal 32023.883) |
|---|---|---|
| none, via xcrun (SDK 27.2) | `air64_v29-apple-macosx27.2.0`, AIR 2.9 | |
| none, no SDKROOT | `air64_v27-apple-macosx15.0.0`, AIR 2.7 | same |
| 27.0 | `air64_v29-apple-macosx27.0.0`, AIR 2.9 | `air64_v28-apple-macosx27.0.0`, AIR 2.8 |
| **26.0** | **`air64_v28-apple-macosx26.0.0`, AIR 2.8** | `air64_v28-apple-macosx26.0.0`, AIR 2.8 |
| 15.0 | `air64_v27-apple-macosx15.0.0`, AIR 2.7 | same |

- **What 26.0 changes in the IR** (27B47, all 175 TUs, `ir/diff-27-26.txt`): 144 TUs identical apart from
  the triple and the `air.version` node. The other 31 (recursion step/sort kernels, zkp mdiv/eval/mix/pv/ntt_x,
  12 keccak witgen arms + scatter, rv32im misc/witgen_tu/accum_tu, groth16 witness_poly/ntt/msm_sort/msm_window)
  differ in 464 lines, all of them barrier and atomic intrinsic signatures: `air.wg.barrier` (180),
  `air.atomic.global.or` (164), `.load` (66), `.add` (24), `air.simdgroup.barrier` (30). AIR 2.9 adds one
  argument (`air.wg.barrier(i32 2, i32 5, i32 1)` vs `(i32 2, i32 1)`; the atomics gain an `i32 0`). No
  other instruction differs.
- **The SDK version** goes into every module as `!"SDK Version"` (xcrun's `SDKROOT`). IR made with SDK 26.5
  and 27.2 (26.0 target) is otherwise identical in all 175 TUs (renumbered metadata only).
- **`MACOSX_DEPLOYMENT_TARGET`** is honoured by `metal` (26.0 → `macosx26.0.0`), so it would silently
  change the target under an unchanged cache key: refused by `metal-tc.sh`'s wrapper (exit 1 with a message,
  tested), `assemble-macos.sh` (all modes) and `Makefile.mac`.

### Kernel cache keyed by the target

- risc0-build-kernel's key is a SHA-256 over flags, SDK, sources and the compiler's `--version` first
  line. With the wrapper the line carries the target, so the key does. Evidence: building the 27.0 kit
  and then the 26.0 kit in the same clone left **two** entries per library in the (isolated) cache
  (`metal_kernels_zkp-d902550f…` 27.0 and `-bb61bb75…` 26.0, likewise groth16, keccak, recursion, rv32im),
  and `check-macos-release.sh --binaries` confirms every embedded metallib's target.
- **Not done: a separate cache *directory*.** risc0 derives it from `$HOME` (`directories::ProjectDirs`);
  zk-miner cannot move it without changing `HOME` for the build, which risc0-build passes to the guest
  builds and which changes the guests' image ids (B9-DEP). The key (plus the MTLB check) gives the
  isolation the brief asks for; a risc0-side cache-dir override would be the clean fix (B9-PKG open issue 4).

## 3. Compiler: 27B47 pinned, Xcode 26's toolchain obtained and rejected

- **Xcode 26's toolchain can be obtained here, user-locally.** Apple's index maps Xcode 17F113 (26.5) to
  Metal Toolchain **17F109**; the asset server answered for it (`tc26/asset-17F109.json`); the `.aar`
  (687,865,856 B) matched its published SHA-1 and SHA-256; decrypted, unpacked and mounted without sudo:
  `Apple metal version 32023.883 (metalfe-32023.883)`, its binaries `minos 14.0, sdk 26.4`, dmg sha256
  `67258e0c…924d98`.
- **Compared on all 175 TUs at 26.0:** same AIR version and identical `ir_scan` rows, but **23 TUs
  differ in code** (260,179 diff lines): groth16 `msm_window` (83,548), `g12_bench`, `g9_bench`,
  `msm_reduce`, `bn254_test`, zkp `poseidon254` (52,848) and `pv`, the rv32im `eval_check_ef*` variants (288-898
  each), recursion `eval_check_split*`, zkp `mix`/`mdiv`/`ntt_x`, groth16 `ntt`/`witness_poly`. Shipping it
  would need the whole stress/suite/A-B round again for a second compiler, for no gain.
- **Decision (b): CI uses the pinned, validated 27B47.** Its binaries are `minos 14.0`, so it runs on the macOS 26
  runner. `scripts/ci/fetch-metal-toolchain.sh` downloads it from Apple's CDN, checks the `.aar` SHA-256
  `fcea0f3c0b038950bfe1c838ec05af56589b62591c9f9892457bfc1e2b6513d9`, decrypts with the asset's published
  key, unpacks, checks the dmg SHA-256 `9a7f61869f1ec662b69634db473f81d7b18f947e9cd81601d4b2825f903b6265`
  and mounts it. Tested end to end here: 18 s, the dmg matched the one every validation used, a rerun reuses
  the mount; then detached and deleted.
- **For B9-CI** (also `docs/macos-beta.md` "CI"): toolchain 27B47 / metal 32023.922; kernels
  `-mmacosx-version-min=26.0` (AIR 2.8, MSL 3.2) through `metal-tc.sh`; binaries minos 26.0; archives
  `metal-tt` 27B47 `-macos-version-min 27.0` key `macos27`, family g17s. Caveat: the runner's Xcode 26 SDK
  puts `SDK Version 26.x` into the AIR (only difference, measured), so its metallib digests (and archive
  names) differ from this Mac's kit, built with SDK 27.2 (`BUILDINFO` `metal_sdk=27.2`).

## 4. Runtime API audit (macOS 26)

Binaries: the 26.0 kit worker and CLI (`api/`).

- **C imports** (`dyld_info -imports`, 334 worker / 251 CLI): every system symbol is exported by the
  **macOS 26.5 SDK's `.tbd` files**; the only misses are 8 of the worker's own C++ weak definitions
  (`<weak-def-coalesce>`: nvtx, poolstl). Framework imports: IOKit (8: power sources, registry), CoreFoundation,
  Metal (`MTLCreateSystemDefaultDevice` only), CoreGraphics (`CGMainDisplayID`, `CGDisplayIsAsleep`),
  libobjc; the CLI adds Security (SecureTransport, `SecTrust*`), SystemConfiguration (proxies), Foundation
  (`NSFoundationVersionNumber`). All are macOS 10.x-era APIs.
- **Objective-C** (no `.m` sources anywhere: everything goes through `msg_send!`/`sel!`, so the selectors are
  C strings, and `-Wunguarded-availability` has nothing to compile): the 6,571 method / property / class
  names of the 27.2 SDK's Metal, Foundation, CoreFoundation, CoreGraphics, IOKit and QuartzCore headers
  were indexed with their `macos(...)` annotations and intersected with the binaries' strings: 69 (worker)
  and 6 (CLI) are used. **None is missing from the 26.5 SDK headers, and none is annotated after 26.0.** The
  newest: `architecture` (14.0, and the HAL checks `respondsToSelector:` first), `gpuAddress` (13.0),
  `isLowPowerModeEnabled` (12.0, also behind `respondsToSelector:`), binary archives (11.0). No MTL4, no
  residency sets, no `MTLLogState`.
- **sysctl names** (strings of the binaries): worker `hw.memsize`, `hw.optional.armv8_2_sha512`,
  `kern.memorystatus_vm_pressure_level`; CLI also `machdep.cpu.brand_string`, `vm.pagesize`, `vm.page_*`:
  all predate macOS 26.
- **External commands:** the worker runs `/usr/sbin/sysctl` only.
- **Findings: none to guard.** No `crates/**` change was needed.

## 7./8. What this Mac cannot validate; the macOS 26 VM check (blocked)

- **The VM check could not run.** tart 2.41.1 was installed user-locally (below) and the image pulled, but
  Virtualization.framework refuses to start a macOS guest from this session, twice:
  `VZErrorDomain Code=-9 "The virtual machine encountered a security error." … "Failed to get current host
  key." … "Failed to create new HostKey." (NSPOSIXErrorDomain 22)`. Cause: no user is logged in at the console
  (`/dev/console` owned by root), the agent runs in a `Background` launchd session over SSH, and the login
  keychain is locked ("User interaction is not allowed"). A macOS VM needs its host key from the user's
  keychain, i.e. a logged-in GUI session; nothing user-local fixes that without the user's password. **Not a
  kit finding.** To run it: log in on the Mac's console (or Screen Sharing), then in Terminal
  `/Users/user/zkminer/bin/tart pull ghcr.io/cirruslabs/macos-tahoe-base:latest && tart clone … zkminer-m26 &&
  tart set zkminer-m26 --cpu 4 --memory 8192` and `gpu-run --tag B9-M26-vm -- scratch/w9/B9-M26/vm/s1.sh` (the
  session script: key, guest facts, quarantined kit, README install steps, CLI, smoke, crash reports).
