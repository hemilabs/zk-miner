# M1: zk-miner Metal worker (`zkminer-prove-risc0-metal`)

Item M1 of the risc0 Metal-port plan (`deps/risc0/docs/metal-port/PLAN.md` 4.6 row M1, errata 8.1
zk-miner bullet, 9.1). Branch `item/M1` of zk-miner (worktree `/Users/user/zkminer/zk-miner-wt-M1`,
based on `metal` 921a229), building against the merged fork at `../deps/risc0` (`zkminer/metal`
464e69b89: R8-R10, C9, K5, Z7, G7 merged). Files: `crates/zkminer-prove-risc0/{Cargo.toml,
src/main.rs}`, new `src/metal_host.rs` and `tests/metal_worker.rs`, `Cargo.lock`.

## What was done

There is no CUDA source to port; each piece follows the existing `cuda|rocm|intel` arms of the same
worker and the fork's Metal entry points.

### Cargo.toml
- `[[bin]] zkminer-prove-risc0-metal` (`src/main.rs`, `required-features = ["metal"]`).
- Feature `metal`: the PLAN 8.1 fan-out (`risc0-zkvm/metal`, `risc0-groth16/metal`,
  `risc0-circuit-keccak/metal`) **plus** optional deps the worker calls directly: `risc0-zkp`
  (`hal::metal::device_name`), `risc0-circuit-rv32im` and `risc0-circuit-recursion` (`metal_warmup`,
  `release_cached_provers`), `risc0-groth16-sys` (`metal_warmup`, `metal::working_set_budget`), and a
  macOS-only `metal = "0.29"` (the fork's version) for `recommendedMaxWorkingSetSize` and
  `currentAllocatedSize`. Deviation from the 8.1 line: those extra entries; nothing else changes.
- `Cargo.lock`: the `metal` crate family (block, foreign-types, core-graphics-types, objc, ...)
  enters the lock because the feature makes it reachable.

### src/metal_host.rs (new, `#[cfg(feature = "metal")]`)
- `support()`: refuses with a clear message (logged once) when the build is not aarch64, the
  process runs under Rosetta (`sysctl.proc_translated`), there is no Metal device, the device is not
  an Apple unified-memory GPU, or `hw.memsize` < 12 GiB (8 GB Macs; PLAN 9.1 "not supported" tier).
- `working_set_limit()` = min(`recommendedMaxWorkingSetSize`, `RISC0_METAL_MAX_WORKING_SET_BYTES`
  (fork grammar via groth16-sys), `ZKMINER_CUDA_VRAM_BYTES` (the dispatcher's `hw.memsize - 8 GiB`,
  M2)).
- `job_po2_for_limit()` / `default_job_po2()`: the default segment size from that limit (table
  below), never above `RISC0_DEFAULT_JOB_PO2` (20).
- `keep_groth16_cache(limit, po2)`: keep the Groth16 key (5.7 GB) between proofs only if
  `limit >= stark_peak(po2) + 5.93e9 + 12 GiB` (the headroom is the host-side state that shares
  unified memory: ~13 GB measured, see below). The 36 GB dev machine (28.1 GiB) releases; a 48 GB Mac
  (~36 GiB) keeps.
- `PeakSampler`: polls `currentAllocatedSize` every 2 ms, peak per named phase.
- `warm_up_pipelines()`: once per process, rv32im(+zkp), recursion, keccak (K5 archive) and
  groth16-sys PSOs on four threads in parallel, timed and logged ("cold" if > 10 s).
- `release_after_proof()`: drops this thread's recursion provers and logs the GPU memory held.

### src/main.rs
- `detect_gpu()` metal branch: `(true, device name)` from `support()` (which uses
  `risc0_zkp::hal::metal::device_name()`), `(false, None)` on an unsupported Mac.
- `gpu_refusal()`: Prove, CalibrateSegmentLimit, Benchmark, Warmup and `--benchmark` refuse on an
  unsupported Mac (`--benchmark` exits 2 with the message; Benchmark answers an empty result).
  Execute/ProgramId (CPU) still work.
- `default_job_po2()` replaces `RISC0_DEFAULT_JOB_PO2` wherever the host names no size
  (`job_segment_po2`, `run_proof_once`, `benchmark_program`, warm-up); non-Metal builds unchanged.
  A host-named po2 above the Mac's table value is proven as asked (the guest can tell its size, so
  the worker must not change it) but logged as a warning.
- `release_groth16_cache_if_tight()`: Metal arm decides from the working-set limit and the default
  po2 (`keep_groth16_cache`), not from `ZKMINER_CUDA_VRAM_BYTES` alone.
- `release_after_proof()` (all backends: the Groth16 decision; Metal: plus the recursion provers)
  after every proof, failed or not: Prove, benchmark, calibration, warm-up.
- Metal `warm_up()`: refusal check, `groth16_component::ensure_installed`, then (except on a
  dedicated measure worker: `ZKMINER_RISC0_EXECUTE_MAX_RSS_BYTES` set and no VRAM env)
  `warm_up_pipelines()` and one verified fibonacci(1000) Groth16 proof at the default po2. Also run
  before `--benchmark` and the Benchmark command.
- `self_vmrss_bytes()` on macOS: `task_info(MACH_TASK_BASIC_INFO).resident_size`, so the existing
  RSS self-guard (`ZKMINER_RISC0_EXECUTE_MAX_RSS_BYTES`) now works on Macs too.
- Peak GPU memory per phase logged for every proof (`proof`, `held after release`) and per benchmark
  program (`segments`, `recursion`, `wrap`, `held after release`).

### Default segment size (PLAN 9.1)

| working-set limit | po2 | STARK peak, segments / recursion phase (MiB) | typical Mac |
|---|---|---|---|
| < 6 GiB | 17 | 2082 / 3971 | 16 GB base chip under a ~4 GB owner-active cap |
| 6 to < 12 GiB | 18 | 2700 / 4390 | 16 GB Mac (~10.7 GB recommended; 8 GiB host figure) |
| 12 to < 20 GiB | 19 | 4976 / 6668 | 24 GB Mac (16 GiB host figure) |
| >= 20 GiB | 20 | 9473 / 11169 (up to 10089 / 11987 for bigint-mul) | 32 GB+ (28.1 GiB here) |

The Groth16 wrap needs about 7.4 GB by itself (5.7 GB key plus the identity_p254 recursion), see the
budget runs.

## Assumed / not verified
- **Cold pipeline build not observed**: every run found the pipelines warm (0.1 s: rv32im+zkp 0.0,
  recursion 0.0, keccak 0.1, groth16 0.0 s). The metallibs are byte-identical to the ones other agents
  already built on this machine, so the OS shader cache and the keccak archive hit. Cold numbers from
  the unit notes: rv32im eval_check ~54 s (R6), recursion 47-75 s (C4), keccak ~25 s with the archive
  (K5), groth16 343-355 s (G7). The parallel warm-up and the "cold" label are untested on a cold
  cache.
- Refusal paths (Intel Mac, Rosetta, 8 GB, non-Apple device) were not exercised on such hardware;
  `this_mac_is_supported` covers the accepting path only.
- Table rows for 16/24 GB Macs are derived from budget runs on the M5 Max, not measured on those
  machines; their `recommendedMaxWorkingSetSize` (~10.7 GB at 16 GB) is from the plan, not measured.
- The macOS `self_vmrss_bytes` compiles and is used by the existing self-guard, but no test reads it and no ballooning guest was run against it.

## Known gaps / issues addressed to later items
- **zkvm owner (M3 follow-up)**: no public way to drop the cached segment prover. A proof that
  fails before its wrap leaves the segment prover's pool (2-10 GB) allocated until the next proof.
  On success the zkvm's own post-wrap `release_hal_buffers` drops it (measured: 49 MiB held after
  every proof). Exposing `risc0_zkvm::release_hal_buffers()` (pub) would let the worker call it
  after a failure. Running proofs on a throwaway thread is NOT an alternative: `CACHED_SEGMENT_PROVER`
  is `ManuallyDrop`, so its buffers would leak.
- **G8 (groth16 metal.rs)**: `gpu_prove` starts the key loader *before* running `pre_gpu`
  (`release_hal_buffers`), so the key load races the release of the STARK pools. Under a budget the
  load is checked against memory about to be freed and fails (8 GiB, po2 18, memory-merkle:
  "4602757120 bytes already allocated"); without a budget the wrap peaks at STARK + key (16.6-17.6 GB
  at po2 20 instead of ~7.4 GB). Fix: run `pre_gpu` before spawning the loader, or retry the load
  once after `pre_gpu` on a budget error. The prestart preload during identity_p254 has the same
  effect. Until then a 16 GB Mac cannot wrap a multi-segment proof under an enforced 8 GiB budget.
- **Minimum tier (PLAN 9.1)**: the wrap alone needs ~7.4 GB, so under a ~4 GB owner-active budget no
  Groth16 proof is possible on Metal (clean refusal). G10's levers (compact coefficients, mmap) apply.
- **Performance (R13-R15, C11, Z10)**: STARK ~147K c/s at po2 20 (~6.7 s per 2^20 segment). The
  wrap's 16 s is mostly identity_p254 on the CPU (Z10).
- **M2 / M4 (host side)**:
  - `risc0_job_po2` gives 20 to any card with >= 14 GiB host VRAM figure; on a 24 GB Mac (16 GiB)
    the worker's table says 19. The host should size Metal from the same table (or ask the worker).
  - The benchmark took ~19.4 min; the dispatcher's 600 s proving timeout fired mid-benchmark
    ("Proving timeout (600s) exceeded for risc0:metal:0") and only failed to kill the worker because
    the pid identity check cannot read `/proc` on macOS. Raise the Metal benchmark timeout or shrink
    the inputs, and fix the macOS pid identity check.
  - `zkminer benchmark` device row shows "po2 24 / 16M rows / 16.0 GB" for the uncalibrated Mac;
    those columns come from the host, not the worker.
  - Workers cannot be memory-capped on macOS (no systemd) and the `/proc` leak scan is skipped.
  - GPU power falls back to 300 W (M2 known gap).
- **K5 / packaging (M4/M5)**: ship or pre-build the pipelines at install (`zkminer` sends Warmup
  before benchmarking, which now builds all four circuits' PSOs before any timed proof).
